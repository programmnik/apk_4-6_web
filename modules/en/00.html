Introduction

What are these lab papers about?

Working with the operating system kernel is like exploring a hidden mechanism that controls everything that happens on your computer. When you open a file, run a program, or connect to a network, it is the kernel does all the heavy lifting, and your program just asks it to do so through special "doors" — system calls.

In these laboratory works, we will lift the veil and look inside this mechanism. We will learn not just to use system calls, but also to intercept them — to replace the standard behavior of the system with your own code. This is not just a hacking technique, but an important tool for debugging, monitoring, and auditing security.

During these laboratory work, you will:

  • find out what the system call table is and how the kernel finds the right handler;
  • write your first kernel module that will intercept the system call and log which files they open on your system;
  • learn different ways to find the address of the system call table, from simple to advanced;
  • get acquainted with the modern kprobes mechanism, which allows you to monitor the kernel without modifying it.

These laboratory works are a bridge between the theory of operating systems and real practice. After completing them, you will stop perceiving the kernel as a "black box" and begin to understand how your programs actually work on the lowest level.

What awaits you in these laboratory works

Direct address substitution in the sys_call_table during compilation

Let's start with the simplest way. You will find the address of the system call table in the system file. System.map, write it into the module code and build the module. You will learn:

  • what is the System.map file and how it helps to navigate the kernel;
  • how to use commands grep and awk to extract addresses from system files;
  • how to write a script to automatically substitute the address into the code;
  • how to build and load kernel modules on Linux.

Dynamically determine the sys_call_table address during module loading

A hard-coded address works, but only until the first kernel update. Here, we will learn to determine the address of the table automatically right at the time of loading the module. You will learn:

  • get the kernel version through the file /proc/version and the global variable init_uts_ns.name.release
  • read files from the kernel space using filp_open and kernel_read
  • make modules portable between different kernel versions.

Using the kprobes and kretprobes mechanism

A modern and secure way of interception that does not require changing the system call table and disabling memory protection. Instead, the kernel itself inserts "traps" into the required functions. You will learn:

  • how the kprobes tracing mechanism works;
  • how to intercept the entry and exit from system functions;
  • how to analyze the return values of system calls.

Useful functions for developing kernel modules

Let's explore some important functions that will be useful when writing modules:

  • kstrtoul — safe conversion of strings to numbers;
  • copy_from_user — safe copying of data from user space;
  • kallsyms_lookup_name — searching for kernel symbol addresses by name.

Why is it needed

The skills you'll gain open doors to various fields:

  • Monitoring system development: tracking which files and network connections are opened programs.
  • Security audit: understanding how attackers can hijack system calls and being able to detect such attacks.
  • Debugging and tracing: a tool for "eavesdropping" on programs' interactions with the kernel.
  • Understanding the OS: you will see how the kernel works at the code and memory level.

After completing these labs, you will not only be able to pass the assignments, but also use this knowledge in real-life projects.
