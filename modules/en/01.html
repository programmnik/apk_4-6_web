System Calls in Linux

What Are System Calls?

A system call (syscall) is a mechanism by which a program requests services from the operating system kernel to perform privileged operations.

When your program needs to:

  1. open a file,
  2. allocate memory,
  3. create a process,
  4. send data over a network,
  5. read data from the keyboard,

it cannot do this directly (this is impossible in user mode) — instead, it requests the kernel's services through a system call.

A simple analogy: A system call is like calling the hotel front desk. You cannot go into the storage room and take a towel yourself, but you call the reception, and an employee brings it to you. The kernel is the reception desk, and the system call is the phone number.

Why Are System Calls Needed?

Reason Explanation
Security A user program cannot directly manipulate hardware or the memory of other processes. All operations go through the kernel, which checks access rights.
Abstraction Programmers don't need to know exactly how a hard drive, network card, or graphics card works. The kernel provides a unified interface for working with devices.
Resource Control The kernel can manage process priorities, allocate CPU time, monitor memory usage, and prevent system overload.
Stability Buggy code in a user program cannot crash the entire system — the kernel isolates processes from each other.

CPU Operating Modes

Modern processors support at least two operating modes with different privilege levels:

Mode Name What Is Allowed
Ring 3 User Mode Limited instructions, access only to its own memory, direct hardware access is prohibited.
Ring 0 Kernel Mode All instructions, direct access to memory and devices, interrupt management.

The transition from user mode to kernel mode is called a context switch. This is an expensive operation, so system calls are designed to be as fast as possible.

On modern 64-bit Linux systems, a system call is executed using the syscall instruction (on x86-64). On older 32-bit systems, the int 0x80 instruction was used.

How Does a System Call Work?

The process of executing a system call can be broken down into several stages. Figure 1 shows the path of a system call from user space to the execution of kernel code.

Stages of System Call Execution

Step 1. The user enters the ls command in the terminal. The ls program calls the getdents() function from the C standard library (glibc) to get a list of files in a directory.

Step 2. The glibc library prepares the arguments (a pointer to a buffer for writing directory entries, buffer size) and places the system call number into a CPU register:

  1. On x86-64, this is the rax register.
  2. For the getdents system call, the number is 78 (defined as __NR_getdents in kernel header files). For getdents64 (the modern version), the number is 217.

Step 3. A special CPU instruction is executed, which switches the processor to kernel mode:

  1. On x86-64 — syscall.
  2. On x86 (32-bit) — int 0x80.

Step 4. Control is passed to the system call handler in the kernel (usually the function entry_SYSCALL_64 or system_call).

Step 5. The handler uses the number 78 (or 217 for getdents64) from the rax register to find the appropriate function in the system call table sys_call_table.

Step 6. The corresponding kernel function — sys_getdents() (or sys_getdents64) — is executed. It reads the directory contents from the file system and builds structures with file names.

Step 7. The result (the list of files in the directory) is returned back to the ls program in user space.

Step 8. The processor switches back to user mode. The ls program receives the data and displays it on the screen as a table.

Key point: All of this happens in microseconds, and the program doesn't even notice the context switch!

System Call Table (sys_call_table)

The sys_call_table is an array of pointers to kernel functions. Each system call has its own number (index in the table). Using this number, the kernel finds the address of the handler function and passes control to it.

How Does the Kernel Find the Handler?

When a system call occurs:

  1. The kernel takes the number from the rax register.
  2. Uses this number as an index into the sys_call_table array.
  3. Gets the address of the handler function.
  4. Passes control to that address.

For example, when a program calls openat(), the number 257 is placed in the rax register. The kernel accesses sys_call_table[257], gets the address of the sys_openat function, and executes it.

How to View the System Call Table on Your System

Above we examined the sys_call_table in theory. But how can you see it on your own system?

In Linux, there are several ways to see which system calls are available and what their numbers are.

View System Call Numbers

System call numbers for your architecture are defined in kernel header files.

For 64-bit systems:

cat /usr/include/x86_64-linux-gnu/asm/unistd_64.h

For 32-bit systems:

cat /usr/include/x86_64-linux-gnu/asm/unistd_32.h

Example output:

#define __NR_read 0
#define __NR_write 1
#define __NR_open 2
#define __NR_close 3

View function addresses in memory

The file /boot/System.map-$(uname -r) contains the addresses of all kernel symbols, including sys_call_table.

grep sys_call_table /boot/System.map-$(uname -r)

Example output:

ffffffff81a001c0 R sys_call_table

Or

ffffffff81a001c0 D sys_call_table

  • D(Data) — the symbol is located in the initialized data section of the kernel (.data). This section readable and writable
  • R(Read-only) — the symbol is located in the read-only section (.rodata). This section is only readable (a write attempt will cause a kernel panic).

View the Table in a Debugger

If you have the gdb debugger and kernel debug symbols installed, you can load the kernel into the debugger and view the table:

gdb /usr/lib/debug/boot/vmlinux-$(uname -r)
(gdb) print sys_call_table

View via /proc/kallsyms

If your kernel is built with CONFIG_KALLSYMS support (usually enabled), you can view the addresses of symbols:

cat /proc/kallsyms | grep sys_call_table

Example output:

ffffffff81a001c0 R sys_call_table

This method may produce unexpected output: 

0000000000000000 R sys_call_table

Modern Linux kernels use the KASLR mechanism (Kernel Address Space Layout Randomization). To make it more difficult for attackers to hack the system, the actual physical addresses of kernel functions and variables are hidden. To see the real addresses, you need to run the command with superuser privileges:

sudo cat /proc/kallsyms | grep sys_call_table
